## [Unreleased] · Korean version changed

### Prepare for real-world testing

- The source of the official Splunk Attack Range has been fixed as a commit, and optional Compose and installation/inspection commands for the local management API and web UI have been added. User cloud authentication files are not connected, and creating a lab server is a separate step.
- Added optional SSO setup/login commands using AWS CLI in official images. We only use private folders dedicated to our projects and do not create cloud servers or connect to management APIs.
- Added AWS Windows single target private setup preparation/Terraform plan review and 4-hour end data generator for each session. Default passwords, public access, proprietary tags, and termination protection are checked, and the actual scheduled installation and server creation on AWS is a separate verification step.
- We support existing local AWS CLI authentication and Seoul region plan review, and have strengthened the processing of actual AMI output, unconfirmed default security group, and incomplete termination inquiry. Termination permissions are reviewed by a separate session policy using roles pre-created by the administrator.
- Added 1~168 hours manual operation and Windows `t3.medium` selection for user-directed cleanup. Using the same reviewed plan, we created 3 servers in the Seoul region, 150 GiB disks, and NAT, and checked the actual ownership tags and execution status. I have not installed an automatic shutdown schedule.
- After installing the official role, we verified Splunk collection of actual Sysmon 1·Security 4688·PowerShell 4104 with unique execution marker·host·time range. The original evidence, access password, and manual organizing data were excluded from Git, and the aggregation and verification scope were recorded in the public document.
- We re-checked actual request, audit, and schedule alarms in the existing WAF/Splunk environment, and strengthened verification to check whether the practice file was actually delivered or not with the target file hash.

### AegisLoop actual execution loop

- Closed-loop Added Re-validate actual ARTEX · Gather evidence from Files/Splunk · Propose candidates based on baseline audit logs · Save revision · Re-run new validation UUID · Abort · Export original JSON to the Closed-loop main tab. Retains the existing Offline Log Rule Evaluation tab.
- Distinguish between actual existing alerts by run and baseline/candidate shadow matches from the same rerun audit log. Collection errors, missing fields, and incomplete ranges are preserved as unverifiable, and accuracy, false positive rate, MTTD, and MTTR are not calculated just by running two attacks.
- Prevents duplicate attacks by generating request UUID and expected revision, and preserves the base/new rerun pair of a loop and the rule, source, and basis hashes. Candidate storage does not automatically apply production SIEM rules, and separate deployment helpers are limited to local, isolated Splunk practices.
- The actual UI/API order and support limitations have been reflected in the [User Guide](docs/aegisloop.md). AWS is a temporary demonstration environment and is not a long-term service infrastructure.

### AegisLoop’s first MVP

- An integrated overview and Offensive·Defensive·Closed-loop menus were added, and the existing ARTEX diagnostic dashboard was maintained in Offensive.
- Added independent defense incidents starting from files/Splunk logs without vulnerabilities, and immutable evidence and AI investigation run/stop/recover/export.
- Offline field rule candidate creation, evaluation, and history with separate label logs for improvement and evaluation have been added. Metrics are calculated from input and specify duplicates, missing fields, and undefined denominators. This tab does not execute attacks or deploy operational rules.
- Added [Source Analysis](docs/aegisloop-source-analysis.md) and [User Guide and Synthesis Example](docs/aegisloop.md).

### Localization (i18n)

- **User-exposed output is forced to be in Korean.** The action guide body (brain) of the benchmarked agent is left in the original text to preserve performance, and only the output visible to the user (vulnerability report, fact summary, final summary, chat response) is written in Korean through a code fixation segment (`langDirective`). The original text of commands, payloads, codes, and logs is preserved.
- **Moved the web UI to Korean.** Introduced `next-intl` in Next App Router and separated the string into `web/messages/ko.json` and `web/messages/zh.json`. The original Chinese is preserved in `zh.json` to compare with upstream updates. Screen strings such as dashboard, vulnerability, conversation, notification sending, interception, and LLM settings were moved to Korean.
- **User exposed errors/responses in the server API have been moved to Korean.** HTTP error/response phrases returned to the browser have been replaced with Korean. However, the original text of the text fed back as input from the agent brain was maintained to prevent benchmark drift, and the basis for the decision was recorded in the repository work document.
- **The document was reorganized into Korean.** The Korean `README.md` was created and the English `README.en.md` was placed together, and the original Chinese was preserved as `README.zh.md`.

### Defense/detection data

- **Defense/detection guide added.** We have created a Korean guide ([`docs/defense-ko.md`](docs/defense-ko.md)) that explains how autonomous AI attacks are different from existing scanners, fingerprints (IoCs) observable by defenders, entry points and hardening, detection rules, and incident response, as well as an English version ([`docs/defense-en.md`](docs/defense-en.md)) with the same content.
- **Provides detection rules for distribution.** The text in the guide has been translated into ready-to-use rules. The host/log layer uses [Sigma](https://sigmahq.io) atomic/correlation rules ([`detections/sigma/`](detections/sigma/)), and the network layer uses enrich probes and [Suricata](https://suricata.io) rules targeting the User-Agent of norma SDK WebFetch ([`detections/suricata/`](detections/suricata/)). I put it in.
- **ATT&CK coverage has been visualized.** The rule tagging technique has been organized into the MITER ATT&CK Navigator layer ([`detections/attack/`](detections/attack/)).
- **Machine-readable indicators of compromise (IoC) are provided in a standard format.** The unique fingerprints exported by ARTEX are collected in one file as CSV ([`detections/indicators/artex_indicators.csv`](detections/indicators/artex_indicators.csv)), and the same indicators are stored as MISP events ([`detections/indicators/artex_indicators.misp.json`](detections/indicators/artex_indicators.misp.json)) that can be imported directly into the threat intelligence platform. The indicator supported by the rule is `to_ids`, and the host forensic port is marked as a clue for classification.
- **Reproducible detection tests have been added.** Eight types of tests that actually run and prove the rules (Sigma structure/compile verification, Sigma real-time event matching, backend portability, SigmaHQ convention lint, Suricata load/ignition, ATT&CK layer matching, index-source matching, MISP export ↔ CSV synchronization) and a batch runner/pre-commit example that runs them all at once were added and connected to the CI merge gate. Sigma Real-Time Event Matching not only compiles the rules, but also verifies both atomic and correlation rules to ensure that malicious sample events are actually fired and normal events are silenced.

### storage maintenance

- **Security/abuse warnings and domestic law notices have been added.** Scope of use, information and communications network act/personal information protection law notices, and warnings against abuse have been added to the top of README.
- **Replaced screen preview with Korean UI screenshot.**
- **We have overhauled the maintainer runbook and contribution guide.** We have created a runbook ([`MAINTAINING.md`](MAINTAINING.md)) and a detection rule contribution contract ([`CONTRIBUTING.md`](CONTRIBUTING.md)) to prevent upstream synchronization and translation drift. The runbook also summarizes the build assumptions of the release publishing pipeline and the procedures for verifying those premises locally without tags.
- **Added Push/PR Merge Gate CI.** Upstream repositories only run CI in tag releases, but this fork runs Go builds/static analysis (`go vet`)/unit tests ([`ci.yml`](.github/workflows/ci.yml)) in all pushes and PRs, Korean UI static builds ([`web.yml`](.github/workflows/web.yml)), and inside the document repository. Turn on link/image referential integrity ([`docs.yml`](.github/workflows/docs.yml)) to catch regressions that occurred during the Koreanization process before merging. Integration tests that require a database are validated together with an isolated PostgreSQL service per package. Document link checking is powered by a deterministic script ([`scripts/check-doc-links.py`](scripts/check-doc-links.py)) that does not depend on external networks, preventing multilingual documents from merging with many relative links pointing to each other and broken screen preview images. Document anchor (`#헤딩`) links are also compared with headings using the same slug rule as GitHub, and table of contents and cross-reference links that were quietly broken due to changes in heading letters are captured together. The detection rule suite is handled by the merge gate described in the ‘Defense/Detection Data’ section above.
- **External link survival is periodically checked.** External links such as incident reporting window and standard reference pointed out by the defense guide are flaky depending on the remote server status, so they are excluded from the merge gate, and non-blocking workflow ([`external-links`](.github/workflows/external-links.yml)) is run every Monday and manually to track browser User-Agent·GET·redirect. Turn check ([`scripts/check-external-links.py`](scripts/check-external-links.py)). In cases where the host is alive but the verification method is blocked (bot blocking, speed limit) and upstream inherited dead links (allowlist) that we cannot fix are not marked as failures, they are shown in red only when an external link curated by our document is newly broken.
- **We have a contribution/governance infrastructure.** Bug/feature/translation issue template ([`.github/ISSUE_TEMPLATE/`](.github/ISSUE_TEMPLATE/)), pull request template ([`PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md)), security vulnerability reporting policy ([`SECURITY.md`](SECURITY.md)), and action We have established a code ([`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md)) to ensure that external contributors submit issue, PR, and security reports in a consistent format.
- **Completed English documentation layer for international contributors.** Although Korean is the primary language of this repository, we have included English versions of the core documentation so that contributors, security researchers, and defenders who do not read Korean can reach the same information. In addition to the English `README.en.md`/Defense Guide ([`docs/defense-en.md`](docs/defense-en.md)), change history ([`CHANGELOG.en.md`](CHANGELOG.en.md)), security reporting policy ([`SECURITY.en.md`](SECURITY.en.md)), and behavior Code of Conduct ([`CODE_OF_CONDUCT.en.md`](CODE_OF_CONDUCT.en.md)), Contribution Guide ([`CONTRIBUTING.en.md`](CONTRIBUTING.en.md)), Maintainer Runbook ([`MAINTAINING.en.md`](MAINTAINING.en.md)), Traffic Proof Design Document ([`docs/finding-traffic-evidence-en.md`](docs/finding-traffic-evidence-en.md)), and We have an English version of the bug, feature, and translation issue templates.
